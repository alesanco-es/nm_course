Lab 1 — SNMP and Python

Network Discovery, Device Inspection, and Monitoring

Author

Álvaro Alesanco Iglesias

1 Context

SNMP (Simple Network Management Protocol) remains one of the most widely used mechanisms for retrieving status and operational information from network devices.

In this lab, we will use a MikroTik router as the managed device and Python to develop simple network management and monitoring tools.

The lab follows a progression similar to that used by real network management platforms:

  1. Discover which devices are present in the network.
  2. Identify which devices can be managed using SNMP.
  3. Inspect the information exposed by those devices.
  4. Explore their interfaces and other objects available through their MIBs.
  5. Monitor how selected network parameters evolve over time.

Throughout the lab, you will work directly from a Linux system and use both command-line tools and Python scripts.

2 Learning Objectives

After completing this lab, you should be able to:

  • prepare a Python environment on Linux for developing simple network management tools;
  • understand the relationship between OIDs, MIBs, scalar objects, and tables;
  • perform SNMP queries using GET, GETNEXT, and WALK;
  • interpret SNMP responses and the VarBind structures exchanged between manager and agent;
  • modify managed objects using SET when permitted by the agent;
  • automatically discover devices on a network and determine which of them provide SNMP management;
  • retrieve and interpret the interface table of a network device;
  • use SNMP counters to calculate traffic rates;
  • develop a simple interface monitor using Python;
  • understand the fundamental differences between SNMPv1, SNMPv2c, and SNMPv3.

5 First Contact with SNMP

We now have the tools required to act as an SNMP manager. The next step is to configure the MikroTik router as an SNMP agent and perform our first query.

5.1 Configuring the MikroTik SNMP Agent

Connect to your MikroTik router and verify the SNMP configuration.

Enable the SNMP agent if necessary and configure the following community:

Parameter Value
SNMP version SNMPv2c
Community public
Access Read-only
Warning

SNMPv1 and SNMPv2c communities are transmitted without encryption and should not be considered secure authentication mechanisms.

We use SNMPv2c here because it allows us to focus first on the SNMP data model and protocol operations. SNMPv3 will be introduced later in the lab.

5.2 Your First SNMP GET

Let’s retrieve sysDescr.0 from the MikroTik.

sysDescr belongs to the system group of MIB-II and contains a textual description of the managed device.

Its numeric OID is:

1.3.6.1.2.1.1.1.0

From the Debian container, execute:

snmpget -v2c -c public <MIKROTIK_IP> 1.3.6.1.2.1.1.1.0

You should obtain a response similar to:

iso.3.6.1.2.1.1.1.0 = STRING: ...

The exact value depends on your MikroTik router.

Notice that the result contains three different pieces of information:

1.3.6.1.2.1.1.1.0  =  STRING  :  value
        │                  │         │
        │                  │         └── Object value
        │                  │
        │                  └──────────── ASN.1 data type
        │
        └─────────────────────────────── Object identifier

This (OID, value) association is the basic information carried by an SNMP VarBind.

Why does the OID end in .0?

sysDescr is a scalar object.

SNMP identifies an instance of a scalar object by appending .0 to the object OID. Therefore, a GET request must use the complete instance OID:

sysDescr.0

Later, when working with tables, the suffix will have a different meaning: it will identify a particular row of the table.

6 GET Operations and VarBinds

In the previous section, you retrieved a single managed object using an SNMP GET operation.

An SNMP GET request, however, can contain more than one VarBind. This allows a manager to request several objects using a single SNMP message.

In this section, we will compare both approaches and examine how SNMP handles errors.

6.1 A Minimal PySNMP Example

PySNMP provides an asynchronous API based on Python’s asyncio.

The following example retrieves sysUpTime.0 from an SNMP agent:

import asyncio

from pysnmp.hlapi.v3arch.asyncio import (
    SnmpEngine,
    CommunityData,
    UdpTransportTarget,
    ContextData,
    ObjectType,
    ObjectIdentity,
    get_cmd,
)


async def main():
    target = await UdpTransportTarget.create(
        ("<MIKROTIK_IP>", 161)
    )

    error_indication, error_status, error_index, var_binds = await get_cmd(
        SnmpEngine(),
        CommunityData("public", mpModel=1),
        target,
        ContextData(),
        ObjectType(ObjectIdentity("1.3.6.1.2.1.1.3.0")),
    )

    if error_indication:
        print(error_indication)
    elif error_status:
        print(
            f"{error_status.prettyPrint()} at "
            f"{error_index and var_binds[int(error_index) - 1][0] or '?'}"
        )
    else:
        for oid, value in var_binds:
            print("OID:  ", oid.prettyPrint())
            print("Type: ", type(value).__name__)
            print("Value:", value.prettyPrint())


asyncio.run(main())

Replace <MIKROTIK_IP> with the address of your MikroTik router and execute the program.

Before continuing, identify in the program:

  • where the SNMP agent is specified;
  • where the UDP port is specified;
  • where the community is specified;
  • where SNMPv2c is selected;
  • where the requested OID is specified;
  • where the program waits for the SNMP response;
  • which variable contains the returned VarBinds.

Why is await appropriate for an operation such as an SNMP request?

6.5 Sequential Requests vs Concurrent Requests

Experiment 1 deliberately performed the seven GET operations sequentially:

GET 1 → wait → GET 2 → wait → GET 3 → wait → ...

However, SNMP requests are primarily I/O-bound operations: most of the time the program is waiting for network responses.

Create a third version in which the seven individual GET operations are started concurrently using asyncio.gather().

Conceptually:

results = await asyncio.gather(
    get_one(OID_1),
    get_one(OID_2),
    get_one(OID_3),
    # ...
)

Measure the execution time.

You now have three different strategies:

Strategy SNMP requests Execution
Individual GETs 7 Sequential
Multiple VarBinds 1 Single request
Individual GETs + gather() 7 Concurrent

Compare the three measured times.

Why can concurrent individual GETs be significantly faster than sequential GETs even though both approaches generate the same number of SNMP messages?

Does concurrency eliminate the network overhead of sending multiple SNMP requests?

Which of the three approaches would you choose for retrieving several objects from one device? Would your answer necessarily be the same if you were monitoring many different devices?

Note

This distinction will become important later in the lab.

When monitoring a single device, grouping several objects into one SNMP request can reduce protocol overhead.

When monitoring many independent devices, asynchronous execution allows the manager to communicate with several agents without waiting for each operation to finish before starting the next one.

7 Navigating the MIB: GETNEXT and WALK

So far, every GET operation required the manager to know the exact OID of the object to retrieve.

But what happens if the manager does not know all the objects available below a particular OID?

SNMP provides the GETNEXT operation for this purpose.

7.1 Using GETNEXT

A GETNEXT request does not ask for the value of the specified OID itself. Instead, it asks the agent for the next OID in lexicographical order.

For example, consider part of the MIB-II system subtree:

1.3.6.1.2.1.1
│
├── 1.3.6.1.2.1.1.1.0   sysDescr.0
├── 1.3.6.1.2.1.1.2.0   sysObjectID.0
├── 1.3.6.1.2.1.1.3.0   sysUpTime.0
├── 1.3.6.1.2.1.1.4.0   sysContact.0
├── 1.3.6.1.2.1.1.5.0   sysName.0
└── ...

If the manager asks for the object following:

1.3.6.1.2.1.1.1.0

the agent should return:

1.3.6.1.2.1.1.2.0

Try it from the command line:

snmpgetnext -v2c -c public <MIKROTIK_IP> 1.3.6.1.2.1.1.1.0

Now try:

snmpgetnext -v2c -c public <MIKROTIK_IP> 1.3.6.1.2.1.1.2.0

and observe the returned OID.

What information must the manager know to perform a GET?

What information must it know to perform a GETNEXT?

Why can GETNEXT be useful when the manager does not know the complete contents of a MIB subtree?

7.2 Building a WALK from GETNEXT

There is no WALK PDU in the SNMP protocol.

An SNMP walk is obtained by repeatedly asking the agent for the next object:

start OID
    │
    ▼
 GETNEXT
    │
    ▼
returned OID ───┐
                │
                ▼
             GETNEXT
                │
                ▼
          returned OID ───┐
                          │
                         ...

The OID returned by one request becomes the starting OID for the next request.

The process continues until the returned OID no longer belongs to the subtree being explored.

8 Working with SNMP Tables

Scalar objects such as sysName.0 represent a single value.

Network management, however, frequently involves collections of similar objects. A router may have many interfaces, routes, neighbours, or addresses.

SNMP represents this type of information using tables.

8.1 The Interface Table

MIB-II provides information about the network interfaces of a device below the interfaces subtree:

1.3.6.1.2.1.2

Explore it:

snmpwalk -v2c -c public <MIKROTIK_IP> 1.3.6.1.2.1.2

The interface table contains information such as:

Object Meaning
ifIndex Interface identifier
ifDescr Interface description
ifType Interface type
ifMtu Maximum transmission unit
ifSpeed Estimated interface bandwidth
ifPhysAddress Physical address
ifAdminStatus Desired interface state
ifOperStatus Current operational state
ifInOctets Received octets
ifOutOctets Transmitted octets

Unlike scalar objects, table objects have an index identifying the row.

For example:

ifDescr.1 = "ether1"
ifDescr.2 = "ether2"
ifDescr.3 = "ether3"

can be understood as:

             ifIndex

               1        2        3
               │        │        │
               ▼        ▼        ▼

ifDescr      ether1   ether2   ether3
ifType       ...      ...      ...
ifSpeed      ...      ...      ...
ifOperStatus ...      ...      ...
ifInOctets   ...      ...      ...
ifOutOctets  ...      ...      ...

The index therefore connects values belonging to the same interface.

9 From Counters to Telemetry

In the previous section, you observed that ifInOctets and ifOutOctets are cumulative counters.

They do not directly tell us the current traffic rate of an interface.

To obtain a rate, the manager must sample a counter at different times and calculate how much it has changed.

9.1 From a Counter to a Rate

Suppose that the value of ifInOctets is measured at two different times:

Time Counter
\(t_1\) \(C_1\)
\(t_2\) \(C_2\)

The average incoming traffic rate during that interval is:

\[ R_{\text{in}} = 8 \frac{C_2-C_1}{t_2-t_1} \]

where:

  • \(C_1\) and \(C_2\) are counter values in octets;
  • \(t_1\) and \(t_2\) are measured in seconds;
  • the factor 8 converts octets into bits;
  • \(R_{\text{in}}\) is expressed in bit/s.

The same calculation can be applied to ifOutOctets.

Important

SNMP does not calculate the traffic rate for us.

The agent exposes a counter. The manager samples that counter and derives the rate.

This distinction between a raw measurement and a derived metric is fundamental in network monitoring and observability.

11.1 Discovering Hosts on a Local Network

If the manager is directly connected to an IPv4 LAN, ARP provides a useful mechanism for discovering active hosts.

Who has 192.168.153.1?
Who has 192.168.153.2?
Who has 192.168.153.3?
...

A device using one of those addresses can reply with its MAC address:

Manager                                  Device

11.2.2 Ethernet and ARP

ARP requests are transmitted inside Ethernet frames.

An ARP request intended for all hosts on the LAN therefore uses the Ethernet broadcast address:

ff:ff:ff:ff:ff:ff

In Scapy, an Ethernet frame can be created with:

from scapy.all import Ether

ethernet = Ether(dst="ff:ff:ff:ff:ff:ff")

Scapy uses the / operator to encapsulate one protocol inside another:

packet = ethernet / ARP(pdst="192.168.153.10")

This represents:

┌─────────────────────────────┐
│ Ethernet                    │
│ dst = ff:ff:ff:ff:ff:ff     │
│                             │
│   ┌─────────────────────┐   │
│   │ ARP                 │   │
│   │                     │   │
│   │ Who has             │   │
│   │ 192.168.153.10?     │   │
│   └─────────────────────┘   │
└─────────────────────────────┘

Inspect the complete packet:

packet.show()

Notice that / does not mean division in this context. Scapy overloads the operator to construct a protocol stack.

11.2.3 Sending and Receiving Packets

Scapy provides several functions for sending packets.

Because we are working directly with Ethernet frames, we will use srp():

from scapy.all import srp

answered, unanswered = srp(
    packet,
    timeout=2,
    verbose=False
)

srp() means approximately:

send and receive packets at Layer 2

and returns two collections:

answered
unanswered

Each item in answered contains both:

packet sent  →  packet received

For an ARP response, the received packet provides the information we need:

for sent, received in answered:
    print(received.psrc)
    print(received.hwsrc)

where:

psrc   → source protocol address → IPv4 address
hwsrc  → source hardware address → MAC address
Scapy and asyncio

The srp() function used here is a blocking operation.

Calling it from an async function does not automatically make it asynchronous:

async def discover():
    answered, unanswered = srp(...)

While srp() is running, the Python asyncio event loop cannot execute other tasks.

For this exercise, this is not a problem. Scapy sends the ARP probes and collects their responses as a single discovery operation:

                    ARP discovery
                         │
       ┌─────────────────┼─────────────────┐
       ▼                 ▼                 ▼
     host 1            host 2            host 3
       │                 │                 │
       └─────────────────┼─────────────────┘
                         ▼
                    ARP responses

We will therefore perform ARP discovery with Scapy first and then use asyncio for the SNMP queries:

        Scapy ARP discovery
               │
               ▼
       discovered hosts
               │
       ┌───────┼───────┐
       ▼       ▼       ▼
     host 1  host 2  host 3
       │       │       │
       └── concurrent ─┘
          SNMP queries
           (asyncio)

This also illustrates an important Python concept:

asyncio provides concurrency only when the operations being called are asynchronous and yield control while they are waiting.

14 SNMPv3 Security Model

SNMPv3 introduces a different security model.

Instead of identifying access using only a community string, SNMPv3 can provide:

  • authentication — verify who sent the message;
  • integrity — detect whether the message was modified;
  • privacy — encrypt the protected part of the SNMP message.

SNMPv3 defines three commonly used security levels:

Security level Authentication Encryption
noAuthNoPriv No No
authNoPriv Yes No
authPriv Yes Yes

The names can be read as:

noAuthNoPriv
   │      │
   │      └── no privacy
   └───────── no authentication


authNoPriv
 │     │
 │     └───── no privacy
 └─────────── authentication


authPriv
 │   │
 │   └─────── privacy
 └─────────── authentication

  -a <AUTH_PROTOCOL> \
  -A '<AUTH_PASSWORD>' \
  -x <PRIV_PROTOCOL> \
  -X '<PRIV_PASSWORD>' \
  <MIKROTIK_IP> \
  1.3.6.1.2.1.1.3.0

where:

-v3   SNMP version 3
-l    security level
-u    username
-a    authentication protocol
-A    authentication password
-x    privacy protocol
-X    privacy password

Compare this command with the SNMPv2c equivalent:

snmpget -v2c -c public <MIKROTIK_IP> 1.3.6.1.2.1.1.3.0
